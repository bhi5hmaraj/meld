## 2. What meld is

meld is a Claude Code plugin. It runs several coding agents on one request. Each agent works in its own git worktree or jj workspace under `/tmp/meld/<run>/`. The agents share a task board, and meld merges each finished task into an integration line. One agent declares the final commit, and the person delivers it from the pane.

```
Claude Code session
├─ main session + meld plugin ........ commands, the pane, the guard of Claude workers
├─ Claude workers (subagents) ........ their board calls run in the plugin
└─ meld mcp (Bun, one per session) ... board file, ACP runner, socket for the pane
   └─ Codex / Gemini / Cursor workers (ACP processes)
      └─ meld mcp --worker (one each) ... the board tools of that worker
~/.meld/meld.db ← every board read and write, from every process
```

The code has three parts:

- `core/`: the rules and the steps of a run, with no engine code. Each function takes the ports that it uses and no more (`core/ports.ts`).
- `hooks/`: the Claude Code host. `hooks/register.tsx` is the one file that calls the engine.
- `mcp/`: `meld mcp` on Bun, in three modes: the plugin mode (the store and the ACP runner of a session), `--chat` (the tools of the main session for an MCP client), and `--worker` (the board tools of one ACP worker).

The section "Development" of the README gives one line for each file.

## 3. How a run works

1. **Start.** `/meld --agents opus,codex <request>`. `opus` is a Claude worker and `codex` an ACP worker. `MELD_ACP_AGENTS` adds ACP agents. meld makes one workspace for each worker from HEAD, saves the run on the board of the session, and starts the workers. A Claude worker starts as a subagent. An ACP worker starts through `meld mcp`, which gives it a `meld mcp --worker` of its own.
2. **Work.** Each worker reads the board, plans tasks, claims one, commits in its workspace and calls `finish_task`. The board call of a Claude worker runs in the plugin. The plugin commits at the version that it read, and tries again after a lost race (8 tries). The board call of an ACP worker runs in its own `meld mcp`, as one SQLite transaction. `finish_task` merges the commit into the integration line.
3. **Restarts.** Each worker has one host. The plugin restarts Claude workers at the end of each main-session turn, and after a steer or a pane button. `meld mcp` restarts ACP workers at the end of each prompt and every 500 ms, for the board that it leads (`lead_board`). An idle worker goes on in its own session while its context fills less than half of its window. Else a new agent starts with the handover of the old one.
4. **Messages.** From the plugin to a Claude worker: SendMessage. From the plugin to an ACP worker: `send_worker`, a new prompt after the current one. A board call in `meld mcp --worker` that sends to an agent, or shows a toast, writes a row to the table `actions`. The leader `meld mcp` sends the rows for ACP agents every 500 ms. The plugin takes the other rows at the end of each turn of the main session or of a Claude worker.
5. **Pane.** The pane draws the copy of the run in the session state. The plugin updates the copy after each write that it makes. Every 3 s, it also reads the board over the Unix socket of `meld mcp`.
6. **Steer, stop, add.** A steer goes into the run, and each running worker gets it. Stop ends each worker, and the workspaces stay. `/meld-add <agent>` adds a worker with a new workspace.
7. **Finish and deliver.** When every task is done, one worker integrates, runs the checks and declares the final commit. `finish` refuses a final commit that lacks the commit of a done task. Deliver merges the final commit into the branch of the person with a merge commit, marks the run delivered, and then removes the workspaces and the branches.
8. **End of a session.** Claude Code sends SIGINT to `meld mcp`, which stops its ACP agents and removes its socket. The subagents end with the session. The board stays. In a new session, `/meld-resume <board>` takes the board 60 s after its last change, and starts its idle workers again.
9. **Chat mode.** `meld mcp --chat`, as the MCP server of a client such as Cursor, gives the tools of the main session. All its workers are ACP agents. Its board is `chat:<folder>`.
10. **Without Bun.** `meld mcp` does not start. The run lives in the session state, no ACP worker starts, and `/meld-clean` finds no records.

## 4. Data on disk

| Place | What it holds |
|---|---|
| `~/.meld/meld.db` (or `MELD_DB`) | The board file: SQLite in WAL mode, open to its user alone (0600). Schema 4. |
| `~/.meld/backups/meld-<UTC date>.db` | One copy each day, made at the start of a session with `VACUUM INTO`. The 5 newest stay. |
| `~/.meld/channels/<pid>.sock` | The socket of each `meld mcp`, where the pane reads its board. |
| `/tmp/meld/<run>/w1`, `w2`, ... | The workspaces. A jj run also has a store folder `jj/`. |
| Branches `meld/<run>/w1`, ... and `meld/<run>/integration` | The lanes and the integration line of a git run. |
| Session state of the engine | The copy of the run (`run`, shape `run-4`), the facts of the pane, the view and the board id. |

The board file has the tables `boards`, `parties`, `members`, `events`, `context`, `actions` and `runs`. [storage.md](design/storage.md) gives the rules of each one. Facts to keep:

- In `MIGRATIONS` (`mcp/sqlite-store.ts`), the step at index N moves a file from version N to N + 1. Add steps, and do not change a step that shipped. A meld that finds a newer schema reads the file and writes nothing.
- A commit compares the version, and holds a lease of 60 s for its session (`LEASE_MS`). A write whose change gives the same run stores nothing.
- Each write updates the record of its run in `runs`, in the same transaction. `/meld-clean` reads the records through the tool `run_records`. meld writes and reads no `board.json`.
- At the start of the plugin mode and the chat mode, `meld mcp` makes the backup of the day, then removes the rows older than 30 days that no step needs. The context rows stay. [storage.md](design/storage.md) gives the steps to restore a backup.
- Change the shape tag of a session-state atom (`run-4`, `facts-1`, ...) when the fields of its value change. A value of an older shape then reads as the initial value.

## 5. Build and check

```
claude plugin validate .
claude plugin test .
bun test mcp/
tsc -p tsconfig.core.json
node scripts/adapters.mjs
node scripts/shots.mjs
```

- `claude plugin test .` runs the `*.test.ts` files with the test kit of the engine. Those files cannot import `bun:sqlite`, so the specs of `meld mcp` are `*.spec.ts` files that Bun runs.
- `tsc -p .` checks the hooks and the tests. It needs the types of the engine, which the engine writes to `.claude-plugin/types/` when it loads the plugin. git ignores that folder.
- The repository has no package file. So the type check of `mcp/` needs a folder with `bun-types` (1.4.4 passes), `@types/node` and `undici-types`, and a tsconfig with `"types": ["bun-types", "node"]` that includes `mcp/` and `types/`.
- To try a change in Claude Code, start it with `claude --plugin-dir <meld folder>`. The engine loads the hooks again at the end of a turn, but not the manifest, and `meld mcp` keeps the code that it started with. After a change in `mcp/` or in the manifest, use `/reload-plugins` or a new session.
- A live run with no person: `claude -p --input-format stream-json --output-format stream-json --verbose --plugin-dir <meld folder> --add-dir /tmp/meld --permission-mode acceptEdits`, with the turns on standard input. `--allowedTools` takes a list and uses up the next word, so give the prompt on standard input.
- A stand-in for Codex: `MELD_ACP_AGENTS='{"codex":["bun","<meld folder>/mcp/stub-worker.spec-helper.ts"]}'`. With `files: a.txt, b.txt` in the request, it plans one task for each file, does the tasks, and integrates.

## 6. Facts of the Claude Code engine, found live

Checked with Claude Code 2.1.317 and 2.1.318.

- A hooks module spells `$` at its call sites. Each hook builds its own `Io` of closures over its own `$`.
- An agent that a hook starts skips that hook. An agent that a timer or a button closure starts skips every hook of meld. So the restarts come from hooks of the main session, and the start, the board tools and the guard of the other tools are three separate tool hooks.
- Each `$.mcp.call` of the plugin goes through the permission check, with meld as the origin. A `tool.check` hook allows the calls of meld to `meld mcp`, and refuses the calls of the model and of other plugins.
- A timer callback runs outside every hook, and its `$.mcp.call` makes the engine ask the person. So the pane timer reads the board with `$.http.fetch` over the Unix socket, which gets no permission check. The socket path must be 100 bytes or less.
- A message (`$.session.send`) to a subagent that ended its turn continues it from its transcript.
- Before such a resume, the engine checks the offer of the agent type, with the engine as the origin. meld hides `meld:worker` from the model, so it offers the type while one of its resumes runs (the counter `resuming`).
- The agent list can show a resumed agent as ended for a moment. meld marks a resumed worker idle after 15 s, or at its hand-back.
- The guard must let each `SubagentHandback` through, as that call ends the run of an agent.
- A board tool of a Claude worker runs inside a plugin hook with a time limit. Do not wait for merges inside a board call: in 0.8.0, a finish waited, and timed out after it saved its change.
- In auto mode, a launch of a worker needs an approval. `spawnVerdict` approves the launches of meld while its run lives.
- At the end of a session, Claude Code sends SIGINT to its MCP servers.
- `turn.step` gives the usage of each model call. The context of a worker is the input, cache creation and cache read tokens of its last call.

## 7. Decisions of the last sessions

- **Claude workers stay Claude Code subagents.** Claude Code can also run behind ACP (`@agentclientprotocol/claude-agent-acp`, on the Claude Agent SDK). The owner chose subagents on 5 November 2026. The reasons: subagents use the plan of the person with no policy question, the permission rules of the person apply to each call, there are no extra processes, and the transcripts stay in Claude Code. A switch needs a test run first: the worker in auto mode, the claude.ai connectors off (`ENABLE_CLAUDEAI_MCP_SERVERS=false`), `usage_update`, and the choice of a model. See the [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) and the [Agent SDK article for Claude plans](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan).
- **One host restarts each worker.** The plugin restarts its Claude workers (`ownedByEngine`), and `meld mcp` its ACP workers (`ownedByAcp`). So no worker gets two agents.
- **Affinity.** A worker goes on in its session while its context fills less than half of its window (`AFFINITY_SHARE`).
- **No `board.json`.** The records of the board file replace it. A folder with no record, from an older meld or from a session without Bun, loses its folder at `/meld-clean <id>`, and its branches stay.
- **A record that meld cannot read is not maybe live.** That rule was for a `board.json` that a run was still writing. `--all` keeps such a folder.
- **Retention of 30 days, and a backup each day**, as section 4 says.
- **0.10.0 holds 0.9 and 0.10.** 0.9 never shipped alone.

[decisions.md](design/decisions.md) holds the 41 older decisions.

## 9. Traps

- A session keeps the `meld mcp` that it started. After an update, it runs new hooks with an old `meld mcp` until `/reload-plugins` or a new session. An old `meld mcp` that opens a newer schema writes nothing, and says so. An old `meld mcp` also has no `run_records`, so `/meld-clean --all` keeps every folder.
- A change function can run more than once, as the stores that compare versions try again. Keep each change pure.
- The merge chain in `core/actions.ts` puts the merges of one process in order. Across processes, the integration line moves by a compare-and-swap of its ref, and a merge that lost the race becomes a task `integrate #N`.
- When you add a port, each of the 10 calls of `sessionStore` in `hooks/register.tsx` needs it. An edit by script must count the calls.
- Each worker gets the rules of meld in its first board reply. A Claude worker also gets the system prompt of the `meld:worker` type.
- The cost in the pane is the cost of the session, so it leaves out the ACP workers.
- jj does not record a new file over `snapshot.max-new-file-size` (1 MiB), so meld cannot read such a workspace. It counts as not readable, never as a workspace with no work.
- meld needs git 2.38 or newer (`git merge-tree --write-tree`), and jj 0.40 or newer.
- `MELD_DB` moves the board file, and the backups and the sockets go next to it. A deep folder can make the socket path too long. The pane then shows the copy in the session state, with no reads over the socket.
- A `~/.meld` folder from before 0.10 can have mode 0755. The files in it are 0600.
- In a cloud session (claude.ai/code), the git proxy refuses tag pushes and branch deletes. The owner does those.
